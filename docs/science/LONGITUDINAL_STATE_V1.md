# ReadRight Longitudinal Learner State v1

Status: `UNVALIDATED_PILOT`
Engine: `longitudinal-state-v1-pilot-2026-09`

## Purpose

ReadRight must preserve what happened across assessment, instruction, transfer, and retention instead of reducing a learner to a mutable current score. The longitudinal layer therefore uses an append-only event ledger and derives current state by deterministic replay.

## Source of truth

The source of truth is the learner event ledger. State snapshots are caches only.

Event examples:

- `ASSESSMENT_EVIDENCE`
- `INTERVENTION_PLAN_CREATED`
- `VERIFICATION_EVIDENCE`
- `HYPOTHESIS_REVISION`
- `TEACHER_OBSERVATION`

Each event stores learner, sequence number, timestamp, source session where relevant, skill/hypothesis/intervention identifiers, payload, and engine version.

Events are never rewritten by the inference engine. If interpretation changes, a new derived snapshot is generated by replaying the original events through the desired engine version.

## Skill progression

The longitudinal verification sequence is:

`ACQUISITION -> INDEPENDENCE -> TRANSFER -> RETENTION`

Definitions:

- Acquisition: the learner demonstrates the taught skill after instruction. It does not imply independence.
- Independence: the learner demonstrates the skill without instructional support.
- Transfer: the learner demonstrates the skill on unseen/equivalent material.
- Retention: the learner maintains the skill on a later check after transfer.

The engine does not permit a retention event to skip missing independence or transfer evidence.

## Regression

Learning state may move backward. A later failed usable transfer or retention check can reopen the current state as `FRAGILE`. Earlier successes remain in the event history and are not deleted.

This is deliberate: learner state represents the best current instructional interpretation, while the timeline preserves the full trajectory.

## Hypothesis revision

Intervention response is preserved as `HYPOTHESIS_REVISION` evidence.

- `STRENGTHEN`: predicted response occurred under interpretable intervention conditions.
- `WEAKEN`: a sufficiently faithful intervention did not produce the predicted response.
- `REOPEN_ALTERNATIVES`: acquisition occurred but generalization did not, or another pattern requires competing explanations to be reconsidered.
- `NO_CHANGE`: response does not materially change the hypothesis.
- `CANNOT_INTERPRET`: fidelity or evidence quality is insufficient to revise the hypothesis.

A deterministic replay reapplies these revisions to the assessment-derived hypothesis set before producing the current bottleneck decision.

## Snapshots

Snapshots contain:

- learner skill state
- current hypothesis set
- bottleneck decision
- verification stage summary
- through-event ID and sequence number
- engine version
- scientific status

Snapshots can be discarded and rebuilt. They are never the sole evidence source.

## Persistence

Pilot persistence uses SQLAlchemy. `DATABASE_URL` can point to SQLite for local development or PostgreSQL for deployment.

Pilot startup can create tables automatically. Production schema evolution should use explicit database migrations before external deployment.

## Safety boundaries

- No event is a clinical diagnosis.
- Teacher observation is stored as contextual evidence and does not automatically override scientific state.
- Retention cannot be inferred from immediate success.
- An intervention failure with poor fidelity must not weaken a hypothesis.
- Historical evidence must never be silently deleted because current state changed.
- Every derived decision remains versioned and replayable.
